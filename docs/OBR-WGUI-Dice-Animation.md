# WGUI Dice Animation in Owlbear Rodeo

## Status

**Proposed architecture**

This document describes how Wanderer's Guide / WGUI dice rolls can be animated inside Owlbear Rodeo by the `Wanderers-owlbear-Extension`.

The preferred design is:

> **WGUI determines the roll result. The Owlbear extension receives a small roll event and recreates the existing WGUI 3D dice animation locally.**

The animation itself should **not** normally be rendered into a temporary video, uploaded, stored as an Owlbear scene asset, or streamed frame-by-frame.

---

# Goals

The feature should:

- Show WGUI dice rolls visually inside Owlbear Rodeo.
- Reuse the existing WGUI 3D dice behavior and visual language.
- Preserve WGUI as the authoritative source of dice results.
- Animate the exact result already generated by WGUI.
- Support one or multiple dice in a single roll.
- Support initiative rolls and normal checks.
- Respect GM/player visibility rules.
- Use combatant/token colors where practical.
- Work even when the normal Owlbear action popover is closed.
- Leave no permanent scene objects behind.
- Avoid storing animation files unless a future feature specifically needs them.

The result should feel like:

> **The WGUI roll happened on the Owlbear table.**

---

# Existing WGUI Dice Implementation

WGUI already has the core renderer needed for this feature.

Relevant code:

- `src/pages/phase1/phase1-dice-3d.tsx`
- `src/pages/phase1/Phase1Workspace.tsx`

WGUI currently uses:

- `open-dice-dnd`
- Three.js
- predetermined d20 results
- per-die labels
- per-die colors
- dice collision sounds
- automatic cleanup after display

The renderer does **not** need a prerecorded animation.

Its useful input is essentially:

```ts
export type Dice3dThrow = {
  name: string;
  die: number;
};
```

WGUI then converts that into an `open-dice-dnd` roll configuration with a predetermined landing result.

Example:

```ts
[
  { name: "Ulysses", die: 17 },
  { name: "Kotsa", die: 8 },
  { name: "Malksu", die: 20 }
]
```

The important architectural consequence is:

> Owlbear only needs the roll description, not the rendered animation.

```text
                       │
                       ▼

               background process
                       │

                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼

                dice overlay
                       │

```

The Owlbear scene itself does not need to contain a dice object.

# Primary Design Decision

## Send roll data, not animation data

Do **not** transmit:

- animation frames
- screenshots
- GIFs
- WebM files
- MP4 files
- captured canvas frames
- serialized Three.js scene state

Transmit a compact event describing the already-resolved roll.

Example:

```ts
type WgDiceAnimationEvent = {
  version: 1;

  eventId: string;
  encounterId: number;

  kind:
    | "initiative"
    | "check";

  title?: string;

  throws: Array<{
    combatantId?: string;
    name: string;
    die: number;
    color?: string;
  }>;

  audience:
    | "public"
    | "gm";

  createdAt: number;
};
```

Example event:

```json
{
  "version": 1,
  "eventId": "dice-23-20261002-001",
  "encounterId": 23,
  "kind": "check",
  "title": "DC 18 vs Reflex",
  "throws": [
    {
      "combatantId": "ulysses",
      "name": "Ulysses",
      "die": 17,
      "color": "#6b3d8a"
    },
    {
      "combatantId": "kotsa",
      "name": "Kotsa",
      "die": 8,
      "color": "#2e4a8a"
    },
    {
      "combatantId": "malksu",
      "name": "Malksu",
      "die": 20,
      "color": "#2e8a5a"
    }
  ],
  "audience": "public",
  "createdAt": 1790970000000
}
```

This is small enough to move as a normal Owlbear extension message.

# Owlbear Broadcast

The preferred room synchronization mechanism is Owlbear's extension broadcast API.

Conceptually:

```ts
await OBR.broadcast.sendMessage(
  "unwhelm.wanderers-guide/dice-roll",
  event
);
```

Other extension instances subscribe to the same channel:

```ts
OBR.broadcast.onMessage(
  "unwhelm.wanderers-guide/dice-roll",
  (event) => {
    // validate
    // enforce audience
    // dedupe
    // open dice overlay
  }
);
```

The broadcast should be treated as an **ephemeral presentation event**.

The authoritative roll remains in WGUI.

---

# Background Page

The current Owlbear extension action UI is a popover.

Dice animation should not depend on the popover being open.

Add an Owlbear background page to the manifest.

Conceptually:

```json
{
  "action": {
    "title": "Wanderer's Guide",
    "icon": "/wanderers-mark.svg",
    "popover": "/",
    "height": 760,
    "width": 560
  },
  "background_url": "/background"
}
```

The background page should be responsible for long-lived extension behavior such as:

- listening for dice events
- optionally detecting new WGUI roll events
- deduplicating events
- deciding whether the current viewer should see the event
- launching the dice overlay

The existing combat tracker remains in the action popover.

---

# Dice Overlay

The preferred visual surface is a temporary full-screen Owlbear extension modal.

Conceptually:

```ts
await OBR.modal.open({
  id: "unwhelm.wanderers-guide/dice-animation",
  url: "/dice-overlay",
  fullScreen: true,
  hideBackdrop: true,
  hidePaper: true,
  disablePointerEvents: true
});
```

The `/dice-overlay` route renders the existing WGUI-style Three.js dice animation.

After the roll has settled and remained visible long enough to read:

```ts
await OBR.modal.close(
  "unwhelm.wanderers-guide/dice-animation"
);
```

No scene cleanup is necessary because no Owlbear map item was created.

---

# Overlay Rendering

The Owlbear dice renderer should reuse the behavior of WGUI's `Dice3dOverlay`.

The ideal implementation is to extract or reproduce the reusable portion of:

```text
WandersGuideUI
└── src/pages/phase1/phase1-dice-3d.tsx
```

The Owlbear extension currently does not include `open-dice-dnd`, `three`, or `cannon-es`, so those dependencies will need to be added if the renderer is copied into the extension.

Expected dependencies include at least:

```json
{
  "open-dice-dnd": "^1.3.1",
  "three": "^0.186.1"
}
```

Use versions compatible with the current WGUI implementation.

---

# Exact Results, Not Re-Rolls

The Owlbear animation must never independently generate a new game result.

WGUI already decided the result.

If WGUI says:

```text
Ulysses d20 = 17
```

the Owlbear renderer must animate a d20 that lands on:

```text
17
```

It must not call an independent random roll and merely display `17` afterward.

The animation is presentation of an existing result.

---

# Roll Sources

The current WGUI code already supports two important sources.

## Initiative

WGUI records initiative rolls in the initiative log.

Relevant helpers already include:

```ts
initiativeRoundDiceKey(...)
dice3dThrowsFromInitiativeRound(...)
```

The Owlbear event can be derived from the newest initiative log entry.

---

## Checks

WGUI stores check rolls in:

```text
dice_roll_log
```

Relevant helpers already include:

```ts
diceRollLogKey(...)
dice3dThrowsFromCheckLog(...)
diceCheckOverlayTitle(...)
```

This provides enough data to recreate the visual throw in Owlbear.

---

# Event Source Strategy

There are two viable ways for the Owlbear extension to learn that a roll happened.

## Option A — WGUI-side event bridge

WGUI explicitly emits or exposes a new dice event when a roll is created.

```text
WGUI roll
   │
   ▼
WGUI event endpoint / realtime event
   │
   ▼
OBR extension
   │
   ▼
OBR broadcast
```

Advantages:

- immediate
- semantically clean
- no roll-log polling
- easy to identify the authoritative event

Disadvantages:

- requires adding an explicit bridge from WGUI to the Owlbear integration

This is the preferred long-term architecture.

---

## Option B — detect a new roll from existing WGUI data

The Owlbear extension is already retrieving WGUI encounter state.

It can compare the latest roll key against the last key seen.

Conceptually:

```ts
const latest = diceRollLog[diceRollLog.length - 1];
const key = diceRollLogKey(latest);

if (key && key !== lastSeenKey) {
  lastSeenKey = key;
  broadcastDiceRoll(latest);
}
```

Advantages:

- reuses the current WGUI data model
- minimal server work
- good first implementation

Disadvantages:

- latency depends on polling
- multiple Owlbear clients must not all rebroadcast the same WGUI event
- initialization must not replay an old roll

This is a reasonable V1 implementation if an explicit event bridge does not yet exist.

---

# Exactly One Broadcaster

A room must not allow every connected client to detect the same WGUI roll and rebroadcast it.

Otherwise one WGUI roll could produce several Owlbear animations.

Possible strategies:

## GM-only broadcaster

Only the Owlbear GM instance detects new WGUI roll-log entries and broadcasts them.

This is simple and appropriate for the initial implementation.

```text
GM extension
  ├── polls/listens to WGUI dice
  └── broadcasts new rolls

Player extensions
  └── only receive broadcasts
```

## Leader election

A later implementation could elect one extension client as the event relay.

This is unnecessary for the initial version unless GM presence cannot be assumed.

---

# Deduplication

Every roll event should have a stable ID.

Preferred source:

- WGUI roll-log ID, when available

Fallback:

- deterministic key already generated from encounter/log contents
- or a generated event UUID associated with the roll

Clients should maintain a small recent-event cache.

Conceptually:

```ts
if (seenEventIds.has(event.eventId)) {
  return;
}

seenEventIds.add(event.eventId);
```

The cache does not need to be permanent.

A bounded in-memory set is sufficient for normal room use.

---

# Stale Event Protection

A user reconnecting to the room should not see an old roll suddenly animate.

Use the event timestamp.

Conceptually:

```ts
const MAX_AGE_MS = 10_000;

if (Date.now() - event.createdAt > MAX_AGE_MS) {
  return;
}
```

The exact threshold can be adjusted.

The important rule is:

> Existing roll history may be displayed in logs, but only genuinely new events should auto-animate.

---

# Audience and Visibility

WGUI visibility rules remain authoritative.

The event should explicitly state its audience.

Initial audiences:

```ts
"public" | "gm"
```

Examples:

## Public check

GM and players can animate it.

## Secret / GM roll

Only GM clients should animate it.

The client should still enforce the audience even if a malformed event reaches it.

Conceptually:

```ts
if (
  event.audience === "gm" &&
  viewerRole !== "GM"
) {
  return;
}
```

Do not rely only on hiding labels after the fact.

---

# Enemy Naming

WGUI already applies GM/player naming rules for enemy dice labels.

The Owlbear event should carry only the name appropriate for the event audience.

For example, if players should not receive the actual enemy name:

```json
{
  "name": "Enemy 2",
  "die": 14
}
```

rather than sending:

```json
{
  "name": "Infernal Blightling",
  "die": 14
}
```

and hiding it in CSS.

---

# Token Color Integration

The current Owlbear extension already supports token-color matching.

Current behavior includes:

- exact combatant/token name matching
- reading the visible background color from supported token SVGs
- manually selecting a fallback token color when automatic extraction is unavailable

That color can improve the dice animation.

Example:

```text
Ulysses token = purple
Kotsa token   = blue
Malksu token  = green
```

Then the corresponding dice can use:

```text
Ulysses die = purple
Kotsa die   = blue
Malksu die  = green
```

This creates an immediate visual relationship between:

- Owlbear token
- WGUI combat row
- animated die

---

# Where Color Should Be Resolved

Prefer resolving the visual color in the Owlbear extension because it already knows the current scene token presentation.

WGUI does not need to know the Owlbear SVG color.

Recommended sequence:

```text
WGUI event
  │
  ├── combatantId
  ├── name
  └── die result
          │
          ▼
OBR extension
  │
  ├── matched token SVG color
  │       or
  ├── saved manual token color
  │       or
  └── WGUI/default dice palette
          │
          ▼
      rendered die
```

This keeps Owlbear-specific presentation inside the Owlbear extension.

# Sound

The existing WGUI animation uses dice collision sounds:

```text
/dice/plastic-1.mp3
/dice/plastic-2.mp3
/dice/plastic-3.mp3
/dice/plastic-4.mp3
/dice/plastic-5.mp3
/dice/plastic-6.mp3
```

These can be copied or otherwise made available from the Owlbear extension's own origin.

Programmatic playback may require the Owlbear extension autoplay permission.

Conceptually:

```json
{
  "permissions": [
    {
      "name": "autoplay",
      "reason": "Play dice roll sound effects for shared Wanderer's Guide rolls."
    }
  ]
}
```

The visual animation should still work if audio playback is unavailable.

---

# Concurrency

A second roll may occur while an earlier animation is still playing.

The initial implementation should use a small queue.

Example:

```text
Roll A arrives
  ↓
animate A

Roll B arrives during A
  ↓
queue B

A closes
  ↓
animate B
```

Do not open several competing full-screen dice modals.

A reasonable policy is:

- one active animation
- short FIFO queue
- bounded queue length
- discard stale queued events

---

# User Controls

Eventually the extension should expose simple presentation settings.

Suggested settings:

- **Show shared 3D dice**
- **Play dice sounds**
- **Use Owlbear token colors**
- **Animation speed** if supported cleanly
- **Reduced motion**

A user who disables 3D dice should still see the ordinary WGUI roll result in the combat/dice UI.

Animation must never be required to know what was rolled.

---

# Reduced Motion

A reduced-motion mode should avoid forcing full physics animation.

Possible reduced-motion presentation:

```text
┌───────────────────────────┐
│ DC 18 vs Reflex           │
│                           │
│ Ulysses            17     │
│ Kotsa               8     │
│ Malksu             20     │
└───────────────────────────┘
```

The same dice event can drive either renderer.

This keeps the event protocol independent of presentation style.

---

# Replay Last Roll

If replay is later desired, do not store the animation.

Store or reuse the roll descriptor.

Example:

```ts
{
  eventId,
  encounterId,
  kind,
  title,
  throws,
  audience,
  createdAt
}
```

Then:

```text
Replay Last Roll
      │
      ▼
load descriptor
      │
      ▼
run local renderer again
```

WGUI's existing dice log is already a natural persistence layer for historical rolls.

A separate animation database is unnecessary.

---

# Alternative 1 — Temporary Owlbear Media Item

Another possible design is:

```text
WGUI
  ↓
render animation to WebM / MP4
  ↓
serve media URL
  ↓
create temporary Owlbear image/video item
  ↓
play
  ↓
delete item
```

This is technically viable but is **not recommended** for the primary implementation.

Disadvantages:

- rendering/capture pipeline
- media encoding
- temporary file hosting
- synchronization delay
- cleanup logic
- stale map objects after failed cleanup
- less flexible labels
- less flexible colors
- more bandwidth
- harder multi-die composition

Use this only if a future requirement specifically needs a prerecorded or externally rendered animation.

---

# Alternative 2 — Hosted Animation Outside the Scene

The extension could host a generated WebM/GIF and display it in an extension UI surface rather than creating an Owlbear map item.

This avoids scene cleanup but still requires:

- capture
- encoding
- hosting
- download latency

It remains inferior to recreating the existing deterministic Three.js animation locally.

---

# Alternative 3 — Owlbear Local Scene Items

Owlbear local scene items are useful because they are temporary and client-only.

A future lightweight renderer could use:

- local billboards
- simple 2D dice graphics
- result badges

This could work well for a non-3D fallback.

However, it is not the best match for the existing WGUI physics-driven 3D dice.

---

# Alternative 4 — Owlbear Effects

Owlbear visual effects could eventually enhance dice results with:

- natural-20 burst
- critical success glow
- critical failure pulse
- screen flash
- sparks
- magical effects

Effects are better treated as **supplemental feedback**, not as the primary dice geometry renderer.

Rebuilding polyhedral numbered dice as a custom GPU effect would create unnecessary complexity compared with the existing Three.js implementation.

---

# Why Local Rendering Is Preferred

## Bandwidth

A normal event is tiny.

A video is not.

## Latency

A local renderer can start almost immediately after receiving the roll descriptor.

A generated video must first be rendered, encoded, made accessible, and downloaded.

## Cleanup

A modal disappears when closed.

A temporary scene item must be explicitly deleted.

## Reuse

The existing WGUI renderer already solves:

- die geometry
- physics
- forced result
- sound
- labels
- multiple dice

## Customization

Local rendering makes it easy to use:

- token colors
- player-safe labels
- different overlay titles
- reduced-motion mode

# Suggested Implementation Phases

## Phase 1 — Local prototype

Goal:

Prove that `open-dice-dnd` works correctly inside an Owlbear extension modal.

Tasks:

1. Add required dice renderer dependencies.
2. Add a local `/dice-overlay` surface.
3. Hard-code one d20 result.
4. Launch the overlay from the extension.
5. Verify:
   - Three.js rendering
   - predetermined landing result
   - sizing
   - cleanup
   - sound behavior

Acceptance:

```text
Click test button
   ↓
d20 visibly rolls in Owlbear
   ↓
lands on requested value
   ↓
overlay closes
```

---

## Phase 2 — Broadcast prototype

Goal:

Prove synchronized room animation.

Tasks:

1. Define `WgDiceAnimationEvent`.
2. Add a namespaced Owlbear broadcast channel.
3. GM sends a test event.
4. All permitted clients receive it.
5. Each client renders locally.
6. Add event deduplication.

Acceptance:

```text
GM triggers one test event
   ↓
GM and players see one animation each
```

---

## Phase 3 — WGUI latest-roll integration

Goal:

Automatically animate real WGUI rolls.

Tasks:

1. Detect new initiative log entries.
2. Detect new dice-check log entries.
3. Ignore existing entries on initial load.
4. Convert entries to dice animation events.
5. Broadcast exactly once.
6. Enforce WGUI audience rules.

Acceptance:

```text
Roll in WGUI
   ↓
existing WGUI result/log updates
   ↓
same result animates in Owlbear
```

---

## Phase 4 — Token colors

Goal:

Match dice visually to Owlbear tokens.

Tasks:

1. Resolve combatant to matched token.
2. Read token SVG background color where available.
3. Fall back to saved manual color.
4. Fall back again to standard dice palette.
5. Send/apply the resolved color to the overlay.

Acceptance:

```text
Ulysses purple token
   ↓
Ulysses rolls purple die
```

---

## Phase 5 — Production controls

Add:

- dice animation toggle
- sound toggle
- reduced motion
- event queue
- stale-event cutoff
- tests
- reconnect behavior
- graceful renderer failure

# Failure Behavior

Dice animation is supplemental presentation.

If the animation renderer fails:

- do not change the WGUI roll
- do not retry the game roll
- do not modify initiative/check results
- do not block the combat tracker
- log the rendering failure
- close the overlay if necessary

The recorded WGUI result remains authoritative.

---

# Security / Trust Boundary

Never trust a broadcast event as authoritative game state merely because it arrived through Owlbear.

The animation event is visual presentation.

Authoritative state remains:

```text
WGUI / Supabase
```

The extension may validate incoming events before rendering:

- supported version
- supported kind
- valid d20 range
- expected encounter
- valid audience
- reasonable timestamp
- bounded throw count
- bounded label length

Example:

```ts
if (
  throwResult.die < 1 ||
  throwResult.die > 20
) {
  rejectEvent();
}
```

---

# Testing

Unit tests should cover:

- event validation
- event deduplication
- stale-event rejection
- audience filtering
- queue behavior
- d20 clamping/rejection policy
- token color fallback
- combatant label handling

Integration/E2E tests should cover:

1. GM receives public roll.
2. Player receives public roll.
3. Player does not render GM-only roll.
4. Same event is not rendered twice.
5. Existing historical roll is not rendered on initial connection.
6. New WGUI initiative roll animates.
7. New WGUI check roll animates.
8. Multiple dice render in one overlay.
9. Overlay closes cleanly.
10. Renderer failure does not break the combat panel.

---

# Recommended V1 Decision

For the first implementation:

1. **Reuse WGUI's deterministic 3D dice renderer.**
2. **Render locally inside the Owlbear extension.**
3. **Use an Owlbear full-screen transparent modal.**
4. **Use Owlbear broadcast for ephemeral synchronization.**
5. **Use the GM extension as the initial single broadcaster.**
6. **Detect new WGUI roll-log entries if no direct WGUI event bridge exists yet.**
7. **Use roll IDs/keys for deduplication.**
8. **Do not create temporary scene assets.**
9. **Do not generate video files.**
10. **Do not store animation data.**
11. **Use Owlbear token/manual colors for dice when available.**
12. **Keep WGUI as the authoritative record of the actual roll.**

# Summary

The existing WGUI dice system already has the expensive part solved: deterministic 3D dice rendering for known results.

The Owlbear integration therefore does not need to transport animation media.

It only needs to transport the intent:

```text
Who rolled?
What did they roll?
What is the label?
Who is allowed to see it?
```

Each Owlbear client can then recreate the animation locally.

The preferred model is:

```text
WGUI result
   ↓
small dice event
   ↓
Owlbear broadcast
   ↓
local Three.js animation
   ↓
temporary modal closes
```

This preserves the architectural rule used throughout the integration:

> **WGUI owns state. Owlbear visualizes state.**
